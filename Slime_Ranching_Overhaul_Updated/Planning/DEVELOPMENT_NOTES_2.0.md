## Shared design principles

> Players should wonder why Stardew never had a slime sanctuary in the first place.

- Make the mod feel native to Stardew Valley: match its tone, pixel-art style, character voices, UI conventions, pacing, and sense of discovery.
- Keep vanilla slimes and the vanilla Slime Hutch unchanged. Domesticated Slimes use the separate Slime Daycare loop.
- Features should support caring for, raising, breeding, protecting, or bonding with slimes. Keep the loop low-pressure: breeding is player-started, no daily maintenance is mandatory, and completed outcomes wait safely for the player.
- Keep the first experience easy to understand while allowing optional collection, hybrid, rarity, and companion depth.
- Limit the player to one active slime companion. Its abilities should complement Stardew progression rather than replace systems such as sprinklers or Junimo Huts.
- Each save has one Slime Daycare building. The player expands it through Robin's existing upgrade chain instead of constructing additional Daycares. Preserve any additional Daycares already present in older saves; do not delete, merge, or migrate them automatically.
- Keep narrative conflicts nuanced and consistent with established NPC personalities; do not present invented mod lore as vanilla canon.
- Scope filter: prefer features that make the sanctuary feel more alive and naturally part of Stardew over isolated mechanics that add friction. Review each feature by asking whether it feels plausible in Stardew and makes players care more about their slimes.
- Prefer stable gameplay services separated from map coordinates, sprites, animations, and UI. Greybox layouts and test movement/footprints before a final art pass.
- Preserve working breeder/incubator logic and existing save data during the restructure. The owner has approved migrating save-specific state from the installation-folder registry to SMAPI save data and entity `modData`; follow the explicit backup and retry-safe migration rules below.
- Initial release targets single-player. Multiplayer support remains deferred until specifically designed and tested.

## Required workflow for Stardew-specific development

Before implementing a feature that depends on Stardew behavior—especially rendering, animation, pathfinding, buildings, events, or native entity lifecycles—follow this sequence:

1. Inspect the relevant decompiled game classes as read-only reference material.
2. Identify the vanilla implementation and supported SMAPI extension points for the behavior.
3. Prefer supported SMAPI/game APIs over Harmony patches. Use Harmony only when no suitable supported extension point exists, and scope any patch narrowly.
4. Make the smallest testable change that proves the behavior.
5. Verify that change in-game before building further features on top of it; record what was verified and any remaining limits.

## Technical and save boundaries

- Use a hybrid of SMAPI save data and entity `modData`; do not use the mod-installation-folder JSON registry for save-specific gameplay state in the 2.0 architecture. Stardew remains authoritative for native entity fields such as animal name, home, age, friendship, and native ID.
- Store save-wide jobs and progression through SMAPI save-data APIs: breeding jobs, incubator state, Rare Lab and Pool bonus state, building upgrades, furniture-slot configuration, quest/cutscene progression, and companion selection. Store identity-bound data on supported entities through `modData`: Domesticated Slime genome/abilities/rarity and individual egg genome metadata. Entity metadata and save-wide state may reference stable native entity IDs as appropriate.
- Name the onboarding progression and its code `Slime Daycare Quest`; store it under the `SlimeDaycareQuest` save-data field.
- Use **Domesticated Slime** as the player-facing and code name everywhere. The new animal type ID, egg item IDs/tags, texture keys, and quest field intentionally break compatibility with pre-reset saves; create a fresh save for testing.
- Tester console commands automatically target the currently loaded save. The dispatcher supplies its save-folder name to existing handlers, so players omit that argument. Help and argument warnings show only arguments players need to enter. If no save is loaded, the command logs a warning and returns without running the handler.
- Keep preferences in `config.json`, not save progression. Preserve the existing external registry as migration input only: back it up, migrate records without loss or duplication, validate reload/recovery, and make the migration safe to retry. Do not delete legacy data until migration is verified.
- Unique genome eggs must not stack with other eggs. Item `modData` can copy across split stacks and does not by itself guarantee distinct genomes won't merge, so explicitly enforce non-stacking and test inventory moves, chest transfers, save/reload, and hatch identity.
- Preserve vanilla Slime Eggs and the vanilla Egg-Press. The starter egg and domesticated breeding loop provide the initial Domesticated Slimes.
- Handle save/reload, duplicate items, interrupted operations, migrations, missing entities, and uninstall/reinstall as explicit lifecycle cases. Back up save-specific mod data before destructive updates; uninstall cannot run cleanup code.
- The repository's `decompiled game` junction points to `I:\Code\Mods\Stardew-Valley\decompiled game`. Use it strictly as read-only reference material. Never edit, format, generate files into, or otherwise modify the decompiled source tree.

### Proposed gameplay/service seams

These are v7's suggested responsibilities and names, not mandated class names. Keep these boundaries even if the implementation uses different types:

- `BreedingService` / `IncubationService`: own cycle timing, selected parents, egg identity, and durable job state; they must not depend on room coordinates or sprite animation.
- `FacilityInteraction`: maps a fixed tile/action to the correct facility UI.
- `ActivityStationDefinition`: data for station/slot ID, tile footprint, approach points, participant capacity, animation ID, activity duration, and eligibility.
- `ActivityManager`: finds installed stations and owns availability, reservation, and interaction lifecycle.
- `SlimeActivityState`: wandering → choosing → approaching → interacting → wandering, with safe cancel/recovery.
- `VisualProxyRenderer`: shows selected parents and incubating eggs without moving the actual animals into specialist chambers or spawning extra roaming animals.

Map coordinates and station definitions should be data-driven so room revisions do not require rewriting gameplay logic.

## Prior feature rules to preserve or explicitly revise

This section captures concrete feature details from the earlier feature specifications. These are design references, not a claim that the current prototype already implements them. Where a newer owner decision conflicts, the newer decision takes precedence.

### Daycare population and activity loop

- The Daycare has 10/20/30 living-slime capacity by building tier. Count slimes assigned to breeder pens as residents. Population UI and hatch behavior must respect the cap: if the Daycare is full, incubation waits at its completion point until the player makes room; never hatch above the cap. If the player permanently deletes a slime to free capacity while full, max out the Mutagenic Pool pity meter and every incubator's Rare Lab pity meter (both Rare Labs after the second incubator is added).
- Slimes wander freely between activities. The latest owner-directed schedule is: roam for a staggered random 2–4 in-game hours; then have a 50% chance to use the nearest suitable available activity for 2–3 hours; repeat. Cap use at four activities per slime per day; after that, keep roaming. Stagger timers so residents do not all choose or use the same station together.
- Station eligibility includes reachability, compatibility, availability, and capacity. A two-slime play activity reserves both places together. A station cannot be double-booked. A slime assigned to a machine/job or companion state is ineligible for recreation. Cancel, room exit, save/load, day transition, slot replacement, and station removal must release reservations and clear temporary visual offsets safely.
- Furniture uses fixed interaction/approach points and configurable participant limits. Use visual draw offsets for bounce/poses; do not move animal collision tiles to animate. Skip or simplify offscreen animations where appropriate.

### Daycare Management Desk

The basic Daycare includes one management desk at a fixed location. It acts as the hub for Sanctuary administration:

- **Slime Registry:** View all resident slimes, their genome and other information, and what each is currently doing. Use the registry to move slimes into or out of the Daycare. When the companion feature unlocks, expose the established identity-preserving companion transfer through this registry; never clone a slime.
- **Furniture and layout:** View furniture recipes the player owns and open **Furniture Edit Mode**. Show all 3/7/15 fixed slots with their contents and empty state. From the desk, place an owned recipe into an empty slot, replace an occupied slot, or remove its furniture. Furniture stays fixed and cannot be picked up or broken directly in the room.
- **Progression:** Show the current Daycare building tier and the breeder/incubator stages it has unlocked. Robin handles Daycare building upgrades through the standard building-construction flow, like a barn upgrade; machine improvements are included with building upgrades, not purchased separately from Marnie. Marnie sells furniture recipes.
- **Slime Wiki:** Browse base, hybrid, and rare slime information, including their abilities and what those abilities do.

Keep this as one desk with clearly separated tabs or sections; it is the in-building management and information hub, not another machine or furniture slot.

### Genetics, identity, and economy references

- **Current base-color ability directions:** Red/Fighter occasionally increases the chance of double monster drops; Yellow/Revealer finds artifact spots or supported hidden clues; Blue occasionally doubles fishing trash or treasure-chest catches only; Green randomly fertilizes eligible existing crops and removes weeds; Orange can double furnace output and cooked-food output; Violet can occasionally double ore from mining; Pink very slowly heals both player health and energy. Exact probabilities, cooldowns, and eligibility limits remain for balancing. Void takes the former Collector function.
- **Green ability proposal from owner:** Randomly add fertilizer to eligible existing crops and remove weeds. The fertilizer source/type, eligible crop states, frequency/chance, and limits need balancing and Stardew API review before implementation.
- v7's example mapping also calls Blue the crop irrigator, Red the fighter, Gold a proposed 5–10% shop-discount type, Prismatic a rideable companion, and Void a storage/item-collection companion. This is historical context; the newer owner decisions supersede it. In particular, Blue only has an occasional chance to double fishing-trash and treasure-chest catches; it does not improve fish quality or irrigate crops.
- Earlier recipe map had Red+Yellow→Orange, Yellow+Blue→Green, Blue+Red→Violet, plus six named two-ability hybrids (Red-Orange, Yellow-Orange, Yellow-Green, Blue-Green, Blue-Violet, Red-Violet). This conflicts with the new “different base species make a two-ability hybrid” rule; the table is historical reference pending the answer below.
- Two base parents of the same type produce that same base type. Hybrids are limited to the two abilities defined by their type. Two mature, eligible Domesticated Slimes with the same exact hybrid type are allowed to breed with each other, and their offspring is that same hybrid type; this does not stack additional abilities. A hybrid paired with a base slime is eligible and produces either the base parent's type or the same hybrid type with equal 50% probability. Two different hybrid types can breed; choose uniformly among the four base-type contributor slots (25% each). If a base type appears in both hybrids, keep both slots, so that species has two chances (50% total); e.g. Red/Blue × Red/Yellow yields Red 50%, Blue 25%, Yellow 25%. Hybrid colors blend their contributing parent colors into one body color rather than displaying the colors as separate patches. Rare slimes cannot breed.
- Egg/genome data formerly listed parent IDs, generation, primary/secondary species, visual color, size, shiny, rarity, mutation, ability IDs, and liked food. ### Technical implementation rules retained from the earlier contract

- **Native versus mod state:** Stardew owns the FarmAnimal's native ID, name, home, age, and friendship. SMAPI save data owns save-wide breeding/incubation jobs, research bonuses, upgrades, furniture-slot configuration, quest progress, and companion selection. Supported entity `modData` owns identity-bound Domesticated Slime genomes and individual egg genomes. Keep `config.json` for preferences only.
- **Save metadata and migration:** Do not extend the installation-folder registry as the 2.0 persistence architecture. Migrate existing external records into the hybrid SMAPI save-data/entity-`modData` model with backup, retry safety, and verification before retiring the old records. Unique genome eggs require explicit non-stacking rules because item `modData` may copy across split stacks and may not prevent unlike eggs from merging. Verify chest/inventory transfers, save/reload, and exact hatch identity.
- **Lifecycle and safety:** Keep recovery for save-data migrations. Reconcile registered animals to live native IDs. Removed animals are detached from active identity without erasing their genome archive. Missing-parent unfinished jobs clear safely; already-produced outputs remain recoverable. Make every transaction atomic against duplicate item/resource creation. Uninstall cannot clean up save-specific data; explain backup/recovery limits.
- **Vanilla boundaries:** Inspect the decompiled implementation and SMAPI extension points before Stardew-specific changes; prefer supported APIs to Harmony and narrowly scope any necessary patch by location and entity. Preserve the Slime Hutch, wild/mine/Secret Woods GreenSlimes, vanilla Slime Egg items/drops/treasure, and vanilla Egg-Press. No global slime behavior changes. The custom Daycare and Domesticated Slime animal are separate systems.
- **Service boundaries:** Keep save-state/lifecycle, genetics, breeding, egg identity, incubation, fixed facility interaction adapters, furniture/activity scheduler, mutation/pity, production/refinery, companion lifecycle, and time effects in separate services. Map coordinates, tile footprints, sprites, animations, and UI are data/adapters; gameplay services must survive map/art changes.
- **Time and random outcomes:** Resolve random outcomes once on the authoritative job start/completion step, persist the chosen result and ready date, and never reroll after reload. Keep day-boundary effects isolated and guarded. Multiplayer is deferred; if reconsidered, host owns rolls, inventory transactions, and machine state.
- **Visual/runtime performance:** Reuse cached textures and precomputed station occupancy where practical; keep animations transient and restore draw offsets on completion, room exit, title return, machine reservation, or slot removal. Test a crowded 30-slime Daycare before finalizing visual work.
- **Build and artifact workflow:** The mod uses C#/SMAPI on Stardew 1.6+. Placeholder art and a greybox layout come first; generated/revised pixel art needs correct sprite-sheet dimensions, origins, collision, layering, and in-game verification. Exterior design selection is deferred. The `decompiled game` junction is read-only and must never receive writes.

## Remaining owner decisions

1. **Release order:** Companions are confirmed for much later. Use v7's three-release order as the working proposal: core Sanctuary/story/breeding; then living Daycare/expansions/furniture/research; then companions. Retained systems are deferred rather than removed.
2. **Spatial room expansion:** The tier and machine progression is set: basic (capacity 10) has one 18-day breeder, one 7-day incubator, and a broken Mutagenic Pool; first upgrade (capacity 20) improves the breeder to 14 days and unlocks the Egg CryoLab, 1% Rare Lab, and a Maru-led mission to repair the Pool; final upgrade (capacity 30) adds a second 14-day breeder, a second 7-day incubator with its own Rare Lab at 5%, and the Gel Refinery. The basic construction price is 10,000g + 350 Wood + 150 Stone + 50 Slime; its three upgrades use farmhouse prices of 10,000g + 450 Wood, 65,000g + 100 Hardwood, and 100,000g. This supersedes the older 25,000g/material-heavy first-upgrade and material-heavy final-upgrade proposal. Define the room expansion for each tier.
3. **Opening event trigger:** The main Lewis → Wizard → Marnie → Robin → starter split → Wizard follow-up → first player-started breeding sequence is mandatory to deliver the starter egg and teach the loop. Specify the save/day/season conditions for Lewis's first visit and the safe trigger window/location for Marnie's post-construction visit; the later milestone interactions are optional.
4. **Specialist facility dimensions and map art:** The continuous-map layout, top-wall glass-front breeder (6 tiles wide at the rear, narrowing to 5 across the angled front, approximately 4 deep), click-from-playroom interaction, player exclusion from chambers, visual proxies, and future 2–3-tile expansion are approved. The first greybox uses a wider 28×18-tile room with an asymmetric lower-right wing, a stepped bottom contour, and a centered entrance; validate its scale and shape in-game, then revise if needed. Decide final incubator and other specialist-facility footprints and art/layering standards after greybox testing. Other measurements shown in `breeder picture.png` remain visual proposals until approved.
5. **Ability scope:** Which proposed abilities are feasible and balanced for the first companion release, and does riding use the same one-companion slot? Companion switching uses the Management Desk's Slime Registry: return the active slime and select its replacement.
6. **Story scene detail:** The potion explosion victim is the Wizard. Its intended effect, exact comic consequence, dialogue, and how much the Guild learns are still writing details to settle without contradicting that decision. The opening quest is mandatory; milestone character interactions after the first-breeding tutorial are optional.
7. **Quest milestones:** Confirm the post-Marnie tutorial completion condition and ensure quest progression remains recoverable if the player misses a visit or skips the split event. The Rare Lab unlocks with the first Robin building upgrade; it is not gated by a first hybrid or first rare slime. After Daycare construction, Robin points the player to Maru; her Mutagenic Pool repair mission is added to the journal on the next wakeup. Deliver 1 Battery Pack, 5 Iron Bars, and 10 Refined Quartz to complete it and activate the Pool, with no building upgrade requirement.
